# Contributing

How to set up, develop, verify, and release changes to this extension.

## Setup

Install the toolchain once:

```powershell
npm ci --ignore-scripts
npm run prepare
```

The install keeps dependency scripts disabled. `npm run prepare` then enables this repository's `commit-msg` hook by setting `core.hooksPath` to `.githooks`.

**Debugging.** Press `F5`. The launch configuration starts `npm: bundle:watch`, builds the extension with source maps, and opens an Extension Development Host. Breakpoints in `src/**` work there. After a change, press `Ctrl+R` in that window to load the latest build.

**Daily use.** Build a package and install it like any other extension:

```powershell
npm run package:local
```

Then run **Extensions: Install from VSIX...** in VS Code and pick the generated `.vsix`.

**Checks.**

```powershell
npm run verify
```

That runs the type check, lint, format check, and tests. CI runs the same commands, but runs the tests on Windows, macOS, and Linux. It also packages the VSIX, which runs `audit:bundle`; `npm run package:local` performs the same packaging step locally.

Linting is `oxlint`, formatting is `oxfmt`, and both are configured in `.oxlintrc.json` and `.oxfmtrc.json`. The type-aware rules come through `oxlint-tsgolint`, and they are why the toolchain is on TypeScript 7.

Two devDependencies represent compatibility targets rather than development tools. `@types/vscode` must not exceed the major/minor version in `engines.vscode`; `vsce` enforces that rule during packaging. The extension bundle targets Node 20, so `@types/node` remains on that major. CI executes on Node 24 and does not exercise the extension host's Node 20 API surface. [dependabot.yml](.github/dependabot.yml) therefore ignores automatic `@types/vscode` updates and new `@types/node` majors. Update these constraints deliberately when either compatibility target changes.

**Commit subjects.** [commit-instructions.md](.github/commit-instructions.md) defines the convention. `.vscode/settings.json` also supplies that file to Copilot when it generates a commit message. Keep the convention focused on writing a subject; the validation machinery belongs here.

Release Please silently ignores a subject it cannot parse: there is no changelog entry, version bump, or error. The same validator, [scripts/check-commit-subject.mjs](scripts/check-commit-subject.mjs), is therefore used in three places:

- The `commit-msg` hook checks a local commit before Git records it.
- [pr-title.yml](.github/workflows/pr-title.yml) checks the pull request title, because squash merging uses that title as the subject on `main`.
- CI checks the subjects added by every push to `main`, including a squash commit.

The hook catches invalid local subjects earliest, and the pull request check catches an invalid squash subject before merge. CI verifies what actually reached `main` and also covers direct pushes. `git commit --no-verify` skips only the local hook. The validator also rejects the `Revert "…"` subject generated by `git revert`; rewrite it as `revert: …`.

## Architecture

The layout follows one rule: **testable modules do not import anything that requires an extension host.** `usage-bar.ts` receives providers through ports instead of constructing them. Only the wiring in `extension.ts` needs to build the real providers; the modules above it remain plain TypeScript that can run under `vitest`.

| File | External dependency | Responsibility |
| --- | --- | --- |
| `extension.ts` | vscode | Activation and wiring. The only module that constructs providers. |
| `settings.ts` | vscode | Reading and writing the settings section. |
| `status-bar.ts` | vscode | Rendering a `StatusBarItem` and its tooltip. |
| `menu.ts` | vscode | Status item menu commands. |
| `claude-api.ts` | `fetch` | Calling the account endpoint and parsing its response. |
| `claude-credentials.ts` | node | Reading token sources: the credentials file and macOS keychain. |
| `codex-appserver.ts` | node | Discovering the CLI, managing JSON-RPC, and parsing replies. |
| `watcher.ts` | node | Watching files with debounce and retry backoff. |
| `claude.ts`, `codex.ts` | node | Resolving provider-specific paths. |
| `usage-bar.ts` | — | Coordinating provider state and rendering updates. |
| `read-coordinator.ts` | — | Deciding which window reads and when. |
| `shared-state.ts` | — | Serializing and validating shared readings. |
| `usage.ts` | — | Shared types and response validators. |
| `configuration.ts` | — | Plain settings values and their constraints. |
| `formatting.ts` | — | Status text, percentages, and durations. |
| `tooltip.ts` | — | Tooltip content and Markdown escaping. |

Four small types preserve that boundary: `CodexProcess`, `LaunchCodex`, `SharedStore`, and `SettingReader`. `CodexProcess` and `SharedStore` are interfaces; `LaunchCodex` and `SettingReader` are function type aliases. Each describes only the VS Code or operating-system capability its module uses, so tests can provide a substitute without starting the real service.

## Tests

Tests cover both providers' response parsers, `watcher.ts`, `formatting.ts`, `shared-state.ts`, and `read-coordinator.ts`. The two heaviest are `tooltip.ts` and `usage-bar.ts` — the latter because a rate-limit wait, a lease, a provider toggle, and a window closing all reach for the same state.

`codex-appserver.ts` starts Codex through `LaunchCodex` for the same reason. Tests can then simulate partial frames, a silent server, or a stop that arrives during startup. A real Codex installation cannot reproduce those cases on demand.

All source and test files are also checked by `tsc --strict`. One `tsconfig.json` covers `src/` and `test/`, so the editor and `npm run typecheck` apply the same type rules. Type checking complements the tests; it is not runtime coverage.

## Scripts

| Script | Purpose |
| --- | --- |
| `clean` | Removes `dist/` and any built `.vsix`. |
| `bundle` | Production esbuild build into `dist/extension.js`, plus `dist/meta.json`. |
| `bundle:dev` | One development build with source maps. |
| `bundle:watch` | Development build that watches for edits. This is the `F5` pre-launch task; reload the Extension Development Host with `Ctrl+R`. |
| `typecheck` | `tsc --noEmit`. esbuild only strips types, so this is the only type check. |
| `lint` / `format` | `oxlint` and `oxfmt`; `format:check` reports instead of writing. |
| `test` / `test:watch` | `vitest`, which runs the TypeScript tests without a build step. |
| `audit:bundle` | Checks the built bundle against the promises under **Data access**. |
| `verify` | The local gate: type check, lint, format check, tests. |
| `vscode:prepublish` | Bundle and audit. `vsce` runs this automatically during packaging. |
| `package:local` | Cleans, then packages a `.vsix` through `vsce`. |
| `prepare` | Points `core.hooksPath` at `.githooks`. `npm install` runs this itself. |

The build writes two untracked files. `dist/extension.js` is the shipped extension. `dist/meta.json` lists every input included in the bundle so `audit:bundle` can inspect it.

## The bundle audit

`npm run audit:bundle` enforces the promises in the README's [Data access](README.md#data-access) section. A reader cannot verify those promises from the status bar, and an unrelated code change could otherwise break them without warning. The script reads `package.json`, `dist/meta.json`, and the built bundle, and fails on any of the following:

| Check | Fails on |
| --- | --- |
| Runtime dependencies | Any entry under `dependencies`. |
| Bundle inputs | An input that did not come from `src/`. |
| Network targets | Any written-out URL other than the one allowed endpoint. |
| `node:fs` members | Anything the bundle reaches for beyond `readFile`, `readdir`, `stat`, `lstat`, `existsSync`, and `watch`. |
| `node:child_process` members | Anything beyond `spawn`, plus a literal `shell: true`. |
| Codex credentials | The literal `.codex/auth.json` path. |
| Keychain verbs | Any password verb other than `find-generic-password`, and `unlock-keychain`. |
| Absolute paths | A rooted path outside the pinned list of two programs the extension starts. |

The module checks used members against an allowlist. This is stricter than rejecting specific write methods: a check for `/\bwriteFile\b/` would not catch `writeFileSync` or another unlisted method. Adding a member to an allowlist is therefore an explicit decision. The audit derives each binding name from the `require` that created it, so bundler renames remain detectable. If it recognizes a `require` but cannot extract its binding, or finds index access such as `fs["writeFile"]`, it fails instead of silently skipping the check.

Three limits are worth stating rather than discovering, because each marks where the audit stops and review begins:

- A URL assembled from parts at runtime is outside the allowlist, which covers addresses written out in full.
- `spawn` is the only way a process starts and `shell: true` is refused, but the program it starts is resolved at runtime, so the audit constrains how rather than which.
- Packaging proves neither that the VSIX installs nor that it activates; the install before approving a release is what covers that.

If a change requires one of these capabilities, it changes the security boundary described in the README. Update the implementation, audit, and documentation together, or redesign the change to stay inside the existing boundary.

## Failure messages

Every read failure uses the same message structure because the tooltip renders that structure directly. The first sentence states what happened. A second sentence, when present, tells the reader what to do and appears on a separate line under a lightbulb. A failure with no action remains one sentence and one line.

Use normal sentence punctuation. The tooltip can split a long message at a full stop, but not at a semicolon.

Write both parts to fit their rendered line. In `tooltip.ts`, the statement has `LINE_COLUMNS - LABEL_COLUMNS` available and the remedy has `LINE_COLUMNS - HINT_COLUMNS`: currently 39 and 58 characters. Longer text wraps, making that failure block taller than the others.

Do not repeat a name in the remedy when the statement already provides its context: _No Claude Code sign-in was found. Sign in to the CLI or extension._

Failure messages also pass to other VS Code windows through the shared entry. Validate them with `validMessage`, not `validLabel`; labels are short text displayed beside a number and have a stricter length limit.

Mark provider-supplied text as `verbatim`. It is displayed unchanged, is never parsed for a remedy, and is limited to two lines instead of being replaced with text written by this extension.

## Provider marks

VS Code renders status bar icons through the codicon pipeline, which requires an icon font. The two provider marks therefore ship in `assets/agent-usage-bar.woff` and are registered through `contributes.icons`. The font is generated with [Fontello](https://fontello.com) from `assets/fontello-config.json`; open that configuration in Fontello to edit or rebuild the marks.

Keep the pinned code points on re-import — `U+E800` for Codex and `U+E801` for Claude — because `contributes.icons` addresses the glyphs by exactly those characters.

## Releasing

Release Please reads the commit subjects on `main` and maintains one pull request titled `chore: release X.Y.Z`. Additional commits update that pull request instead of creating separate releases. The types that affect the version and changelog are defined in [commit-instructions.md](.github/commit-instructions.md).

Two manual decisions are required: merge the release pull request, then approve the registry deployment after testing the packaged extension.

Every push to `main` starts [release.yml](.github/workflows/release.yml). On an ordinary push, phase 1 creates or updates the release pull request and the remaining phases are skipped. When the push is the merge of that release pull request, phase 1 creates the tag and draft release, which enables phases 2–4:

| Phase | What it does |
| --- | --- |
| **Prepare the release** | Refreshes that pull request, or on its merge tags the commit and drafts the release |
| **Verify the release** | Runs the whole of [ci.yml](.github/workflows/ci.yml) again at the release commit |
| **Publish the release** | Attaches the verified VSIX and takes the release out of draft |
| **Publish to …** | Waits for approval, then Visual Studio Marketplace and Open VSX, independently |

The final phase uses one matrix entry per registry. Each entry publishes the VSIX built in phase 2 and receives only its own registry token.

`force-tag-creation` creates the tag in phase 1, together with the draft release. The tag allows later runs to find that release instead of replaying the same history into the next changelog. The tag is therefore public before the release page and VSIX.

Release Please normally changes only `package.json`, `package-lock.json`, `CHANGELOG.md`, and `.release-please-manifest.json`. Source files in the release commit should therefore match the source already reviewed on `main`; review the release pull request if anything else changes.

The final phase waits for approval through the `release` environment, which stores both registry tokens and requires a reviewer. Marketplace versions cannot be replaced after publication, so this approval is the runtime verification gate.

Before approving, download the attached VSIX, run **Extensions: Install from VSIX...**, reload VS Code, and confirm that both status items and their provider marks appear. CI tests the modules, audits the built bundle, and creates the VSIX. It does not inspect the final archive contents or load the VSIX into a running Extension Host. Manual installation is therefore the only check that the produced package installs and starts with its required assets.

**When something fails.** Re-run failed jobs on the same workflow run for a flaky test or expired registry token. GitHub retains the run artifact for thirty days, and the published release keeps its attached VSIX. Both registry commands use `--skip-duplicate`, so rerunning one failed matrix entry does not republish a version that already succeeded.

Do not replace the artifact when the VSIX itself is broken. The manifest has already advanced to that version, and users must be able to trust that the release asset is the artifact CI verified. Push the fix and publish the next version.

If verification fails before publication, the draft release can remain in place; only maintainers can see it. To remove the draft as cleanup, run `gh release delete vX.Y.Z --yes`. Do not pass `--cleanup-tag`: release tags are protected and the early tag is part of the release boundary.

## Release surprises

Some release behavior comes from GitHub settings rather than files in this repository:

| Setting | Required behavior |
| --- | --- |
| `main` ruleset | Reject deletion and non-fast-forward updates, so accepted subjects remain part of release history. |
| `v*` tag ruleset | Reject deletion and non-fast-forward updates, preserving the tag created with the draft. |
| Pull request merge methods | Allow squash merge only. The pull request title becomes the one subject that lands on `main`. |
| `release` environment | Restrict deployments to `main`, require the maintainer's approval, and keep **Prevent self-review** off while there is only one maintainer. |

The following repository details also affect a release:

- [.vscodeignore](.vscodeignore) denies everything and then allows exactly what ships, so a new asset or document is invisible to the package until it is listed there.
- `README.md` is packaged, which makes it the store page: prose fixed there reaches the Marketplace only in a published version. `assets/screenshot.png` is not packaged — `vsce` rewrites the relative link to `github.com/…/raw/HEAD/…` — so the image is served live from `main` and changes without a release.
- Release Please tracks progress through `autorelease:` labels. An open release pull request carries `autorelease: pending`, and that label is how its merge is recognized. Removing it prevents creation of the release.
- A run waiting on the `release` environment still holds the `release` concurrency group, so pushes to `main` stop refreshing the release pull request until the approval is answered.
- Hand edits to `CHANGELOG.md` inside the release pull request do not survive: the branch is rewritten whenever a later commit changes the release notes. Changelog wording is fixed by fixing the commit subject before it lands.
- A `Release-As: X.Y.Z` footer on any commit forces that version outright, and is the only way to reach 1.0, since below it even a breaking change stops at a minor bump. Nothing needs unsetting afterwards, as `bump-minor-pre-major` applies only below 1.0. Do not use `release-as` in [release-please-config.json](release-please-config.json) instead; there it pins the version until someone removes it.
- Workflows for a release pull request opened with the default `GITHUB_TOKEN` wait for manual approval. CI and PR Title are separate workflow runs and may each require **Approve workflows to run**. This approval is optional for the release: phase 2 verifies the exact release commit after merge, and `main` has no required status checks. Pushes and Dependabot pull requests start normally.
